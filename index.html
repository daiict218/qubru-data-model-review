Qubru · commercial-auto data model ◆ Unified Schema ① Customer Model ② Policy Management ③ Quoting & Applications ④ Claim Management ⑤ Billing & Payments

Unified Schema — the Qubru graph target behind all five views

The single combined entity-relationship schema from which all five views can be reproduced — now being mapped onto the Qubru property graph (ADR-035): Salesforce junction objects collapse into :RELATES edges, and type/EAV objects become edge/node properties governed by the Rule Book. The five source views stay unchanged; the Views column shows where each element appears.

54 entities 109 relationships deduped from 77 entity rows · 140 relationship rows graph-mapping in progress

Graph-mapping decisions (ADR-035) — applied so far

  1. Party Relationship + Party Relationship Type (view ①) collapse into one edge Person —related_to→ Person (M:N, self/bidirectional); role/type + dates become edge properties, allowed types live in the Rule Book.
  2. Option A — no party node. The Vlocity Party object is an identity overlay a relational DB needs to graph across Account + Contact + Household; a property graph doesn't. The four real actors — Account, Person (Contact), Organization, Household — are nodes, each carrying a nullable party_id so they can be promoted to a unified party later, and so B2C identity holds today (same party_id ⇒ same party, replacing the old "considered as / identified as" overlay).
  3. Account Contact Relationship (views ①⑤) collapses into Account —has_contact→ Person (M:N); role / is-direct / dates on the edge. New edges added among the four actors (no existing edge removed): Account→Account related_to, Person→Organization works for, Person→Household member of.

  • Endpoint canonicalisation: "Person / Party / Contact" → Party; "Account (Client) / Carrier / Agency / Consumer" → Account; "Policy Type / Product" → Product.
  • Two policy generations kept distinct: Held Product or Service (Asset) (views ①⑤) vs FSC Insurance Policy (views ②④).
  • Graph mapping (in progress): Salesforce junction objects (which exist only because relational DBs can't store M:N) collapse into :RELATES edges; type/EAV objects become properties + Rule Book config. See the green box above for decisions applied.
